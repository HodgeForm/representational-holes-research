# ORB Genesis local companion 0.3

A small executable discovery loop. It searches a fixed grammar over supplied measurements, freezes predictions, scores one new labelled batch, keeps failed candidates, and checks a finite claim with Lean 4.19.0 (core only, no Mathlib).

This folder is a companion to the cellular-automaton study in the repository root. It is not evidence for that Rule 3 / Rule 17 result.

## Honest scope

- The studies here are **synthetic and finite**. H1–H3 are generated by `hard/gen.py`. The phase fixture is `demo-request.json`.
- The built-in baselines are **exact lookup tables**. They abstain on feature vectors they have not seen, so they score 0/8 on H1. A decision tree or a logistic model with an interaction term would also score 8/8 on H1. Beating these baselines is a weak comparison.
- The per-study Lean certificates prove facts about **the exact rows in that file**: a training conflict, and either the held-out predictions or one counterexample row. They say nothing about any other row. They do not prove the rule is true, causal, novel, or better than a strong model. Encoding is trusted: Lean checks the file Python wrote. See `v2/LIMITS.md`.
- Forged certificates are supposed to fail. `H2_forged_status` flips a refuted study to "supported." `H1_forged_rule` swaps in a rule that does not fit the rows. Both must come back `LEAN_FAILED`, with `sorryAx` on the false theorem.
- The slideshow in `demo/index.html` and `demo/shots/` records one session. Re-running the scripts below creates the same scientific outcomes for H1–H3. Run identifiers and timestamps on a fresh discover call differ, so a newly created bundle hash will differ from the hashes embedded in the slideshow.

## Check the hard tests

From this directory:

```bash
python3 hard/run_hard.py
```

Expected closing line:

```
PASS: hard tests H1-H3 match the preregistered expectations.
```

That command regenerates the synthetic requests, re-runs discover and validate in a temporary database, checks the preregistered H1–H3 outcomes, recomputes the committed result bundles in Python, and checks that the forged H2 status is rejected. It does not need Lean. The preregistration is `hard/PREREG.md` (hash in `hard/PREREG.sha256`). The recorded outcomes are `hard/RESULTS.md`.

## Check the per-study Lean certificates

Install [elan](https://lean-lang.org/install/) and the pinned toolchain. This directory's `lean-toolchain` file is `leanprover/lean4:v4.19.0`.

```bash
elan toolchain install leanprover/lean4:v4.19.0
python3 v2/run_certs.py
```

Run that from this directory. The script asks `elan which lean` while standing here, so it picks 4.19.0. Expected statuses:

- `phase_demo`, `H1`, `H2`, `H3`: `STUDY_KERNEL_CHECKED`, and the printed axiom lines say the theorems do not depend on any axioms;
- `H2_forged_status`, `H1_forged_rule`: `LEAN_FAILED`.

`result.json` is a committed replay of the phase fixture so the certificate script has a phase bundle. `v2/run_certs.py` rewrites `v2/certs/` from the committed bundles. A second run on the same files is stable.

## Run the companion on the phase fixture

Standard library only. The default database is `~/.orb-genesis/research.db`. Pass `--db` to keep a run somewhere else.

```bash
python3 orb_genesis.py --db /tmp/orb-phase.db discover demo-request.json > /tmp/phase-frozen.json
python3 orb_genesis.py --db /tmp/orb-phase.db validate RUN_ID demo-labels.json > /tmp/phase-result.json
```

`RUN_ID` is `run.id` in the frozen JSON. The phase fixture has eight conflicting training pairs, selects `phase`, and predicts eight new rows correctly. Its single-field baseline also scores 8/8. This is an acceptance fixture, not a blind benchmark.

Optional Lean check of the fixed collision template (not the per-study certificate):

```bash
python3 orb_genesis.py --lean "$(elan which lean)" verify /tmp/phase-result.json
```

With pinned Lean 4.19.0 the fixed-template check says `KERNEL_CHECKED`. Without Lean it says `NOT_RUN` and still recomputes the search in Python. The per-study certificates are the `v2/` path above. No uploaded Lean source is executed: verification accepts only the generated template.

## Data contract

A request has `title`, `source`, `fields`, `language`, `training`, `validation_inputs`, and optional positive `costs`. Training rows contain `id`, `observables`, and `outcome`. Validation inputs contain `id` and `observables`. Outcomes are submitted later as `[{"id":"...","outcome":"..."}]`.

Use 1–6 lowercase field names and 2–128 rows in each split. Values must be bounded integers, booleans, or short strings. Validation IDs and complete feature vectors cannot overlap training. The software cannot detect hidden target leakage, measurement error, fabricated data, or dependence between samples from the JSON alone.

Validation labels do not participate in search. A run can be scored once. If you use failures to design a new study, those failures are training evidence; obtain a fresh validation batch.

## Bridge

`bridge/bridge.py` only queues studies whose Python recomputation passed and whose per-study Lean status is `STUDY_KERNEL_CHECKED`. Paths are relative to this directory. See `bridge/README.md`. `BRIDGE-PLAN.md` is an undeployed design note.
